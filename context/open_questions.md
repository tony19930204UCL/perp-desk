## 1. S1 資料來源

原問題：美股日線（算 60 日波動）、財報日曆、美國休市日曆從哪裡取得？

### 建議方案

- 美股日線：採用使用者核准、有授權且能匯出歷史日線的單一資料供應商。第一版由使用者提供 CSV 或公開可下載資料，不向 Hermes 交付任何 API key。固定資料版本，保留交易日期、原始收盤價、調整後收盤價、公司行動與取得時間。
- 財報日曆：公司投資人關係網站的已公布日期優先，另由核准的日曆資料來源提供候選日期。逐筆保留來源、取得時間與「已確認／估計」狀態。不能把沒有查到財報日期解讀成三個交易日內沒有財報。
- 美國休市日曆：以 NYSE 官方交易日曆為基準，另核對標的所屬市場。保留全日休市、提早收盤與 America/New_York 時區，不把銀行假日等同美股休市。官方頁面列出交易所假日與提早收盤，見來源 A。
- 日線缺漏、財報日期未確認或日曆失效時，建議標記 data_unavailable 並阻擋該標的 S1 合格判斷，保留原因。這是待核准的資料品質方案，不是已新增策略規則。

### 理由

來源一致、版本固定才可重現。官方財報公告適合確認公司事件，官方交易日曆適合定義交易日。第一版採匯入方式可以避免引入憑證與額外付費依賴，也避免把未知資訊當成無事件。

### 請核准／指定

- 日線與財報資料供應商，以及可用授權、費用上限與匯入方式。
- 60 日波動的報酬定義、是否使用調整後價格、樣本標準差與所需收盤價筆數（SPEC 未定義，不自行決定）。
- 財報日期不確定時的處理，及「長週末」的日曆判定方式。
- SPEC 的「週一 13:45 UTC」與「美股開盤後 15 分鐘」如何取捨。建議以交易所日曆推導開盤後 15 分鐘，處理夏令時間，但這可能改動 v0，未核准前不實作。

## 2. S1 標的清單

原問題：哪些 Binance TradFi 永續算「大型科技股與指數類」？

### 建議方案

- 採用人工核准的固定白名單，不靠 LLM 每週挑選，也不自行用市值門檻擴張 v0。
- 初始研究候選為 NVDA、MSFT、AAPL，以及 Nasdaq-100 指數類對應合約。這些是供使用者核准的底層候選，不是已確認的 Binance 可交易代號，也不是交易建議。
- 開工後從公開 exchangeInfo 取得實際合約代號、交易狀態與 filters，再用交易所官方合約說明確認底層資產與合約性質。不能只憑字串包含股票名稱就視為 TradFi 合約。
- 白名單記錄底層資產、實際 symbol、官方依據與核准版本。只納入已核實符合 SPEC 的大型科技股或那斯達克指數類。排除 pre-IPO、小型股與身份不明的合約。
- 不存在、停牌、資料不足或最小名目與風控不相容就明確標記不可用，不換標的、不提高曝險、不放寬規則。

### 理由

固定白名單可控制研究自由度與可重現性。交易所代號、上市狀態與限制是動態參考資料，應以公開 exchangeInfo 與官方說明核對，而不是照抄 SPEC 的近似值。exchangeInfo 官方資料入口見來源 C。

### 請核准／指定

- 底層候選白名單，是否要刪減或加入其他底層。
- 若候選均無合格合約，是否維持 S1 等待，僅先驗收 feed 的公開行情（建議維持等待，不替換 v0）。
- 里程碑 1 的公開行情測試合約另行核准，它不代表策略白名單或任何開倉授權。

## 3. daemon 執行機器

原問題：daemon 跑在哪台機器（電腦關機會中斷 24 小時與 7 天驗收）？

### 建議方案

- 由使用者指定一台能持續運作的 Linux 主機，使用獨立 perpd Unix 使用者與 systemd service。先決定主機與預算，不自行購買 VPS 或搬資料。
- 本機 WSL 僅用於開發、離線測試及短時公開行情檢查。若要當正式驗收主機，需使用者確認 Windows 與 WSL 不休眠、不關機、網路穩定，並接受中斷後重新驗收。
- 我只提供 unit 檔與安裝說明。由使用者建立帳號、移交 /opt/perp-desk、安裝及啟用服務。
- perpd 管理 engine、data 與風控設定。Hermes 透過 shared 讀狀態、報告，寫新聞與 verdicts，不共享私鑰、不擴張正式部署權限。

### 理由

24 小時與 7 天驗收依賴持續供電、網路及服務生命週期，不應依賴聊天 terminal session。獨立使用者與 systemd 可隔離權限並讓服務不依賴 Hermes 存活。

### 請核准／指定

- 主機、作業系統、管理者與（若需雲端）月費上限。
- 開發 repo 的授權路徑，以及正式部署的移交方式。
- 「連續 24 小時不斷線」是否指原始 socket 完全不中斷，還是服務持續可用且連線輪替無未標記缺口。建議後者，但它是待核准的驗收解釋，不自行放寬。

## 里程碑 1：feed + reference 實作計畫

以下只列計畫，本次不執行。上述待決事項須先取得回覆，不能猜定答案開工。

### 範圍與順序

1. **確定介面與資料契約。** 定義標準化事件的 stream、symbol、交易所事件時間、接收 UTC 時間、單調時計時、來源識別與原始 payload 參照。價格與數量採精確十進位表示，不在 feed 裡產生交易訊號。
2. **先做 reference 的垂直 TDD 切片。** 從公開 exchangeInfo 擷取實際 tick size、step size、MIN_NOTIONAL、交易狀態與原始 filters，保存來源時間與版本至 symbols.json。每日更新，原子替換。失敗時保留最後完整版本並明示過期，無有效快取不能假裝可用。不以 pricePrecision 或 quantityPrecision 代替 filters。
3. **先接一個公開 stream，再逐類擴充。** 依 SPEC 接 bookTicker、aggTrade、depth5@100ms、markPrice@1s、kline_15m 與全市場強平串流。官方文件目前將公開訂單簿與市場事件分列，實作前核對各串流的實際連線路徑，不能假設單一 URL 全部通用（來源 B、D）。只用公開資料，不碰 user-data 或簽名 API。
4. **補齊連線與品質控制。** 心跳、timeout、退避重連、重新訂閱、連線輪替、去重、亂序辨識與有界 queue。持久化原始事件與 gap 紀錄，記錄原因、開始／結束時間、受影響 stream、可觀察的序號範圍與補回狀態。不能由安靜市場直接推斷掉線，也不能承諾所有串流都有可驗證的完整序號。
5. **缺口處理不造資料。** 有公開補抓途徑才補抓，保留 backfill 標記。歷史 bookTicker 或 depth 無法精確重建時保留 unresolved gap，不插值成真實行情。串流中斷超過 SPEC 的 60 秒時，輸出 stale／不可開新倉狀態供後續 risk 使用（里程碑 1 不建立 broker 或改風控設定）。
6. **整合持久化與觀測。** 開發環境保存可回放事件與 reference 版本。輸出 shared/status.json，含連線狀態、最後事件／心跳、重連、gap、丟棄事件與 reference freshness。這只是 feed 健康快照，不提前建置里程碑 3 的 ledger 雜湊鏈或訊號。
7. **部署與 soak test。** 產出使用者可安裝的 systemd unit 與運行說明。經使用者啟用後，先短時 smoke test，再跑連續 24 小時驗收。不把這次文件工作說成完成里程碑 1，也不把 24 小時驗收等同階段 0 的 7 天驗收。

### 測試方式（之後實作時可重跑）

- **TDD 規律：** 每個行為先寫單一測試，實際看到預期失敗，再寫最小實作令其通過，最後重構並跑全套。不要本次寫測試，也不要一次先堆全部測試再寫全部程式。
- **reference 單元測試：** 手造 fixture 覆蓋正常 filters、缺欄位、未知 filter、非交易狀態、無效 JSON、HTTP 失敗、過期快取及原子寫入中途失敗。確認最後完整快取不被損壞，錯誤不產生猜測的限制值。
- **事件解析單元測試：** 每種 SPEC stream 至少一個正常與異常案例，驗證 symbol、時間、價格／數量、重複及亂序辨識。fixture 明示為手造測試，不宣稱是真實行情。
- **本地故障注入整合測試：** 可控 websocket／HTTP 測試伺服器模擬斷線、無心跳、malformed payload、限流、重訂閱失敗、queue 滿、程序重啟與連線輪替。檢查退避、gap 的開始與結束、reference stale 和持久化狀態。用可控時鐘驗證 60 秒中斷門檻。
- **回放測試：** 同一批記錄事件加同一 reference 版本重播，正規化結果與 gap 清單一致。程序重啟後沒有無聲重複或漏失。這只驗證 feed 可重播，不宣稱已完成 S2 交易重現。
- **公開實網 smoke test：** 從核准主機測 exchangeInfo 與每種公開 stream。記錄實際 endpoint、HTTP／訂閱結果及收到的真實事件。受區域限制或無事件時如實報告，不用 fixture 冒充成功。
- **連續 24 小時驗收：** 保存開始／結束 UTC、單調時計時持續時間、程序重啟次數、每個 stream 的訂閱狀態與事件數、心跳紀錄、重連次數、每段 gap、reference 更新結果、資源觀測與原始日誌。無未標記資料損失。是否允許受控連線輪替，依第 3 題核准的定義判定。不達標即失敗或重新起算，不改口算通過。

### 交付及完成判準

- 可重跑的離線測試指令、實際測試輸出、真實行情樣本、故障注入日誌及 24 小時驗收摘要。
- 每個測試結果都對應上述案例，日誌可以追溯原始事件與 reference 版本。
- 沒有 secrets、交易 API 呼叫、live broker、Ops bot、策略規則改動或風控值改動。
- 里程碑完成後 Telegram 回報驗收證據。未達標只回報 blocker，不聲稱完成。
