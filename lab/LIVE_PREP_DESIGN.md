# 實盤準備設計（策略無關的執行層）

建立：2026-10-10，交易台經營者。狀態：設計草稿，尚未實作，沒有任何憑證接觸，沒有任何實單。
範圍：讓紙盤與實盤共用同一套策略、風控、訂單契約，只把「模擬 broker」換成「真實執行轉接層」。本文件只定義成果、不變條件與驗收，不指定逐檔實作。程式一律走外部工程 relay，我獨立驗收。
前提：是否使用真錢、金額（上限 100 USDT）永遠由使用者決定。本文件不授權任何實單。

## 1. 原則

1. 策略層永遠拿不到憑證。憑證只存在於「執行程式」的環境變數，我不讀、不印、不寫入任何檔案或紀錄。
2. 失敗即關閉。任何不確定（結果不明、對帳不一致、時鐘異常、資料過期）都不能被解讀為「可以繼續下單」。
3. 不重複下單。任何重試都必須能證明前一次沒有生效，否則先查詢，不盲目重送。
4. 實盤與紙盤用同一套風控與帳務契約（PAPER-RISK-001 的語意），實盤只會更嚴，不會更鬆。
5. 每一步可稽核：hash 鏈紀錄意圖、請求、回應、狀態轉換。
6. 先模擬、再測試網、最後才可能是真錢。每道閘門都要有讀回證據。

## 2. 架構

```
策略層 (signals, runtime, risk, sizing)  --意圖 JSON-->  執行介面 (ExecutionAdapter)
                                                         |-- SimBroker (紙盤，現有)
                                                         |-- LiveAdapter (新，獨立程序，持有憑證)
LiveAdapter <--> 交易所 REST 與使用者資料串流
LiveAdapter --> 對帳器 --> 帳務與稽核鏈 --> 停機開關
```

- 策略層與 LiveAdapter 之間只傳意圖與回報，不傳憑證。
- LiveAdapter 是獨立 OS 程序，以 systemd 使用者服務跑，環境變數檔權限 600，只有該服務讀取。
- 停機開關是檔案旗標加硬損失上限，策略層與 LiveAdapter 都檢查。

## 3. 執行介面契約（E1）

意圖欄位（策略層給）：intent_id（穩定且唯一）、symbol、side、type（市價、限價 post-only）、qty、reduce_only、stop_price、protective（是否為保護性出口）、created_at、expires_at。

回報事件（執行層給）：ACCEPTED、REJECTED(reason)、PARTIALLY_FILLED(qty, price, fee)、FILLED、CANCELED、EXPIRED、UNKNOWN_OUTCOME。

訂單狀態機（兩種實作都要通過同一組契約測試）：
- NEW → ACCEPTED → PARTIALLY_FILLED → FILLED
- NEW → REJECTED
- ACCEPTED → CANCELED 或 EXPIRED
- NEW 或 ACCEPTED → UNKNOWN_OUTCOME → (查詢後) 轉為上述任一已知狀態
- 終態不可再變化。重複事件必須冪等（同一事件 ID 重送不重複記帳）。

契約測試必須涵蓋：拒單、部分成交、撤單與成交競態、重複事件、亂序事件、結果不明、重啟後恢復、同一意圖重送不產生第二張單、保護性出口永遠可執行（reduce-only）。

驗收：SimBroker 實作該介面並通過全部契約測試。現有紙盤的行為不變（差分測試）。

## 4. 防重單與結果不明

- client order id 由 intent_id 與嘗試序號確定性產生，只使用交易所允許的字元與長度（待官方文件核對，社群資料指出長度 1 到 36，字元集含英數、點、冒號、斜線、底線、連字號）。
- 送單請求逾時或連線中斷 = UNKNOWN_OUTCOME。**絕不重送**。先用 client order id 查單（`GET /fapi/v1/order`，帶 origClientOrderId）。查到就接手，確認不存在才可以以新的嘗試序號重送，且要等到超過交易所的處理視窗。
- 啟動時一律先對帳（第 5 節）再允許任何新單。
- 錯誤碼對應（-1007 類「逾時，狀態未知」等）**待工程單元對照官方文件逐一驗證**，不憑記憶。

## 5. 對帳（E3）

- 每 N 秒與每次重啟後：交易所持倉、掛單、成交、資金費、手續費，對比內部帳本。
- 任何不一致：暫停新進場，保留現有保護性出口，告警，不自動修正。
- 內部帳本以交易所成交為準（實盤），模擬假設只用於紙盤。
- 實際手續費與資金費覆蓋紙盤假設。差異記錄為學習資料。

## 6. 停機開關與硬損失上限（E3）

- 檔案旗標 STOP：存在即禁止新單，只允許 reduce-only 出口。
- 硬上限：單筆含成本損失、UTC 日損失、累計損失（試點期總損上限 10 USDT）。觸發即停並告警，不自動恢復，需要人工清除。
- 交易所端保護：每個持倉要有交易所端的止損單（reduce-only 或 closePosition），不能只靠本地程序。程序死掉時止損仍在交易所。
- 看門：LiveAdapter 心跳與帳本新鮮度。心跳消失 = 告警，不自動重啟成「繼續交易」，重啟後先對帳。

## 7. 憑證與帳戶設定

- API key 權限：只能交易（讀取加合約交易），不開提領。若交易所支援，綁定固定 IP。
- 環境變數檔由使用者建立與填寫，路徑與權限由工程驗收（600，非版本控制）。我不讀。
- 帳戶模式：單向持倉、逐倉、槓桿不高於 3 倍。啟動時用 API 讀回並核對，不符即拒絕啟動，不自動改設定（避免意外改動）。
- 測試網：交易所有獨立的測試網站（社群資料：REST 基底 `https://testnet.binancefuture.com`，WebSocket `wss://stream.binancefuture.com`，需要在該網站自己建立帳號並產生 API key）。**待官方文件核對**。測試網憑證同樣只放在執行程式的環境變數。

## 8. 時鐘、限流、過濾器

- 簽章請求使用 recvWindow，並在啟動與定期校正與伺服器時間的偏差。偏差過大即暫停下單。
- 遵守交易所限流權重。被限流時退避，不放大重試。
- 每個標的的 tick、step、最小名目從交易所過濾器取，不硬編。啟動時比對，變動即停止並要求審查（與紙盤現行規則一致）。

## 9. 單元切分（E1 到 E3）與驗收

| 單元 | 成果 | 驗收重點 |
|---|---|---|
| E1 | 執行介面契約、狀態機、SimBroker 轉接與契約測試 | 契約測試全過。紙盤差分測試行為不變。不引入網路 |
| E2 | LiveAdapter 骨架：簽章、下單、撤單、查單、使用者事件解析、client order id。只對假伺服器與錄製資料測試 | 無網路。無憑證。冪等與結果不明路徑有測試。簽章對官方範例向量驗證 |
| E3 | 對帳器、停機開關、硬上限、啟動閘、心跳 | 各種不一致情境的測試。旗標與硬上限不可被策略層繞過。重啟安全 |
| E4 | 測試網演練 | 需要使用者提供測試網 API key（放環境變數）。演練腳本、紀錄、對帳結果 |
| E5 | 實盤準備審查 | 逐條核對本文件。未驗項目清單。風險清單。**使用者決定是否進入試點** |
