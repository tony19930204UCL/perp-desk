# Observer Console — active research + historical account

This is a **read-only presentation layer**. It does not poll markets, submit/cancel
orders, change research state, write health, alter the default PAPER account, or
discover files. Operator deployment remains separate from engineering CI.

## Data model

The console deliberately keeps two different identities:

- **Historical/default account**: the existing `--status` snapshot and optional
  `--ledgers` allowlist. Its configured default binding is unchanged.
- **Current research**: one explicitly configured discovery root exposed through
  `--research`. A/B/C remain separate research accounts. Their capital, PnL,
  samples and positions are never pooled with each other or with default.

The current-research adapter reads only configured paths under one absolute
research root:

- `reports/latest.json`
- `shared-feed.sqlite3` in SQLite read-only mode
- A/B/C `sim_broker_state` databases in SQLite read-only mode
- an optional operator-owned process-proof JSON

No filesystem autodiscovery or client-selected paths exist.

## Research config

Copy the shipped template and replace only the absolute root with the already
activated research root and, if available, the explicit process-proof file name:

`lab/research_dashboard_config.example.json`

The expected report/broker paths are relative and remain inside that root.
Symlinks, `..`, absolute child paths, malformed configs, missing A/B/C, and root
escapes fail closed.

The optional process proof is **not generated by this dashboard**. If the
operator already has a read-only process/supervisor proof source it may contain:

```json
{
  "schema_version": 1,
  "active": true,
  "observed_at_ms": 1790000000000,
  "proof_kind": "owned_process"
}
```

If it is absent, stale, future, malformed or inactive the dashboard says process
proof is unconfirmed. A runner label, HTTP 200 response or page refresh is not
used as process proof.

## Exact launch

Existing default-only launch remains valid and unchanged:

```sh
python3 lab/dashboard.py \
  --status /ABSOLUTE/EXISTING/status.json \
  --html /ABSOLUTE/CANDIDATE/lab/dashboard.html \
  --port 8767
```

To add the already configured ledger registry and current discovery research:

```sh
python3 lab/dashboard.py \
  --status /ABSOLUTE/EXISTING/status.json \
  --ledgers /ABSOLUTE/EXISTING/ledger-config.json \
  --research /ABSOLUTE/OPERATOR/research-dashboard.json \
  --html /ABSOLUTE/CANDIDATE/lab/dashboard.html \
  --port 8767
```

This requires no Python glue and does **not** require stopping the discovery pump
or old held runtime. The dashboard binds loopback only.

## Endpoints

- `GET /api/status?ledger=<configured-id>`: existing historical/default account
- `GET /api/ledgers`: existing public ledger IDs/labels only
- `GET /api/research`: one configured current-research presentation
- `GET /api/work`: existing work authority
- `GET /api/health`: existing health/incident snapshot
- `GET /`: self-contained observer console

All write methods remain rejected. Host/Origin/cross-site protections remain
unchanged.

## Current research truthfulness

The console distinguishes:

- last successful poll
- report file update time
- latest retained public source, raw receipt and dispatch timestamp
- source age
- configured process proof and proof age
- work-authority update age

A successful HTTP request is not a market-data success.

A/B/C cards use each arm's own broker state for current cash/position/pending
orders/equity valuation and the discovery report for diagnostic/checkpoint,
fees/funding and sample counters. If an open position lacks a current broker mark,
equity and total PnL are explicitly unknown rather than equated to cash.

B 1x is the primary maker model. B 2x is rendered in a separate diagnostic panel
and is never exposed as a ledger/account/strategy selector.

Historical incidents remain visible in Work/Evidence. Old health is labeled stale
and is not silently resolved from fresher work or research evidence.

## Display precision

Financial source strings remain untouched. The browser may show bounded rounded
text for readability, while every rendered financial amount keeps the exact
source string on a focusable `data-exact` node and accessible label. This is UI
rounding only and does not modify Decimal accounting.

## Operator acceptance

After installing candidate files, without restarting trading/research merely for
the dashboard:

1. Start the dashboard with the existing `--status` and optional existing
   `--ledgers`, plus the new explicit `--research` config.
2. Read `/api/ledgers`; confirm default is unchanged.
3. Read `/api/research`; verify research ID/version/start/checkpoint/deadline
   match the already activated root.
4. Verify A/B/C account values against their isolated state without pooling.
5. Verify B 2x appears only as diagnostic.
6. Compare last poll, source receipt/source age and report timestamp with the same
   root. Missing process proof must show unconfirmed.
7. Verify old incidents/hold remain historical/stale instead of being rewritten
   healthy by a fresh research report.
8. Check 390/768/1280 browser layouts and keyboard navigation locally.
9. Confirm no account/research/health/work bytes changed from dashboard reads.

Linux/Windows localhost acceptance is operator-owned; CI fixture evidence is not
operator-host deployment evidence. The console uses only system font fallbacks
(`Noto Sans TC` / `Noto Sans CJK TC` / `Microsoft JhengHei` / `PingFang TC`);
the CI browser fixture installs the Ubuntu Noto CJK system package so the
Traditional Chinese screenshots prove readable glyph rendering without a CDN or
bundled webfont.

## Rollback

Stop only the candidate dashboard process and restart the previously accepted
dashboard command without `--research` and/or with the previous HTML. Do not
stop/restart the research pump, restore a DB, reset an account, change ledger
allowlists, modify health/work, or alter research start/checkpoint/deadline.

## Scope intentionally unchanged

This delivery does not change PR25/PR27/PR31 contracts, the three-arm strategy,
queue 1x/2x rules, fees, funding, risk, storage, source clocks/age/arrival,
chronology, already activated root, orders/fills/ledger/audit, historical default
account, original held runtime, health writer, host/services, cron,
permissions/model/provider or PR21 activation.
